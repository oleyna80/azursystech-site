## 1. Цель документа

Описать систему работы с отзывами для **AzurSysTech**, чтобы:

- отзывы собирались не случайно, а системно
- Google Business Profile и локальное доверие усиливались постепенно
- founder понимал, когда и как просить отзыв
- положительные кейсы превращались в social proof
- негативные отзывы не ломали репутацию из-за отсутствия процесса

---

## 2. Роль отзывов в системе AzurSysTech

### Core role
Отзывы для AzurSysTech нужны как:

- локальный trust signal
- усилитель Google Business Profile
- фактор конверсии для сайта и Facebook
- подтверждение, что это живой сервис, а не “пустой бренд”
- база для future case snippets and proof blocks

### Main rule
Сначала нужно **хорошо выполнить работу**, а потом уже просить отзыв.

---

## 3. Основной принцип

### Review philosophy
Отзывы не должны выбиваться “любой ценой”.

Их нужно собирать:
- мягко
- вовремя
- у довольных клиентов
- после понятного результата
- без давления

### Core rule
Не просить отзыв:
- слишком рано
- у явно недовольного клиента
- в момент, когда вопрос ещё не закрыт
- без понятного результата для клиента

## 6. Who should be asked for a review

### Best candidates
- клиент, у которого задача реально решена
- клиент, который явно доволен
- клиент, который написал “спасибо”, “всё работает”, “очень помогло”
- понятный кейс с ощутимым результатом
- бизнес-клиент с понятной practical value
- home-user, который получил спокойный и удобный результат

### Strong review candidates
- новый ПК “под ключ”
- Wi-Fi + принтер, которые заработали
- рабочее место для малого бизнеса
- маленький офис / кабинет, где удалось быстро всё привести в рабочее состояние
- ситуация, где было 2–3 связанных проблемы и они были решены за один визит

---

## 7. When to ask for a review

### Best timing
Просить отзыв стоит:
- после завершения работы
- когда клиент уже увидел результат
- когда эмоциональное восприятие положительное
- не слишком поздно

### Practical timing logic
Good moments:
- shortly after successful intervention
- after the client confirms everything works
- after a positive final exchange

### Avoid asking:
- до завершения задачи
- сразу в момент стресса
- когда ещё остались открытые вопросы
- если непонятно, доволен ли клиент

---

## 8. Review request strategy

### Main strategy
Review request should be:
- short
- respectful
- optional
- easy to fulfill

### Best framing
Not:
- “нам очень нужны отзывы”
- “оставьте 5 звёзд”
- “помогите продвижению”

But:
- “если вам всё подошло, отзыв будет полезен”
- “если было удобно и полезно, можно оставить короткий отзыв”
- “это помогает развивать локальный сервис”

---

## 9. Review request workflow

### Recommended workflow
```text
Work completed
  → confirm satisfaction
  → identify happy client
  → send short review request
  → if no reply, optional soft follow-up
  → record result
```

### Rule

Do not stack too many asks.
One clear review request is usually enough.
One gentle reminder later is acceptable.

---

## 10. Satisfaction checkpoint before asking

### Before asking for a review, check:

* задача действительно закрыта?
* клиент явно доволен?
* нет ли скрытого недовольства?
* нет ли незакрытых мелочей?
* клиент подтвердил, что всё работает?

### Good signals

* “всё отлично”
* “спасибо, всё работает”
* “теперь всё понятно”
* “да, это помогло”
* “наконец-то заработало”

### If signals are weak

Do not ask immediately.

## 15. Review request delivery channels

### Preferred channels

* direct message
* email
* follow-up message after successful job
* later GBP review link when available

### Rule

Use the channel where the client already interacted comfortably.

### Avoid

* sending review requests through too many channels at once
* asking publicly in comments
* making the request feel transactional

## 16. Review link logic

### Best practice

When GBP is ready, use a direct review link.

### Why

The easier the path, the more likely the review.

### MVP note

Until the profile is fully ready, the process can stay manual / staged.
But the system should be built with a future direct review-link workflow in mind.

## 17. Review tracking system

### Minimum tracking fields

* client_name_or_reference
* service_type
* segment
* date_completed
* review_requested (yes/no)
* request_date
* review_received (yes/no)
* review_platform
* review_link if available
* notes

### Recommended review platforms

* Google Business Profile
* later optional website reuse

### Rule

Track review requests even if the review is not received.

### SSOT tracking location

Primary operational SSOT should be the lead record in CRM once the job is in `won`.

If CRM is not yet fully operational, use a Google Sheet fallback with the same review fields and status vocabulary.

### CRM mapping for review statuses

- `not_asked` = job is completed / `won`, but satisfaction checkpoint is not yet passed
- `ready_to_ask` = satisfaction confirmed and client is a valid review candidate
- `asked` = review request `Follow-up F1` or `Follow-up F2` has been sent
- `reminder_sent` = one soft reminder `Template F1` has been sent
- `review_received` = public review is visible on GBP and the link is captured
- `declined_or_no_response` = client declined, or there was no response after the allowed reminder

### Operational rule

Founder updates review status immediately after each review-related touchpoint.
Do not keep review state only in memory or chat history.

### Later, reviews can be reused on site if:

### Good review themes

## 20. Negative review handling basics

### Core principle

Negative reviews should not be ignored, but also should not trigger emotional replies.

### Response principles

* calm
* short
* respectful
* no public argument
* no blame
* invite to continue privately if needed

### Do not

* argue publicly in long form
* accuse the client
* reveal personal details
* sound defensive or angry
* make legal threats in public

## 22. When NOT to ask for a review

### Do not ask if:

* клиент выглядит недовольным
* задача была частично закрыта
* есть ощущение unfinished state
* был конфликт
* клиент перестал отвечать после работы
* остаётся спор по цене / объёму / качеству

### Why

Bad timing creates bad reviews or awkward silence.

## 23. Business vs home-user review differences

### Business reviews

Valuable because they signal:

* trust
* competence
* local B2B relevance
* small office capability

### Home-user reviews

Valuable because they signal:

* convenience
* clarity
* comfort
* practical help

### Rule

Both matter.
Do not over-prioritize only one category.

## 24. Review request timing suggestions by service type

### Good candidates to ask relatively soon

* new PC setup
* printer + Wi-Fi
* one workstation setup
* home user resolved pain point
* small business practical setup

### Ask more carefully after:

* broader multi-step business task

* tasks where client may need to “test for a few days”

## 25. Review quality goals

### Good review = not necessarily long

A short, real, specific review is better than a generic one.

### Best qualities

* believable
* specific enough
* practical
* human
* local-service feeling

### Avoid trying to force

* long testimonials
* over-scripted reviews
* unnatural language

---

## 26. Founder operational routine

### After each completed job

Founder should ask:

1. was the client satisfied?
2. is this a good review candidate?
3. if yes, has a review request been sent?
4. if no, why not?
5. should this become a future case / note?

### Why

A simple post-job routine makes review gathering sustainable.
