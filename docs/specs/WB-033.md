## Lifecycle transition contract

The controller has one lifecycle state machine with exactly four active states:
`INACTIVE`, `DEFINE`, `EXECUTE`, and `ASSURE`. Reviewer and Verifier are
ordered evidence steps inside `ASSURE`, not lifecycle states. Closeout is an
immutable event that returns the SSOT to `INACTIVE`.

| From | Event and guard | To | Result or constraint |
|---|---|---|---|
| `INACTIVE` | Work Block open; valid specification, resolved Critic, and exact write-set | `DEFINE` | The Work Block is defined. |
| `DEFINE` | Define approved; current Define revision accepted | `EXECUTE` | Candidate implementation may begin. |
| `DEFINE` | `reporting_only` or `cancelled` closeout | `INACTIVE` | A success claim is forbidden. |
| `EXECUTE` | Candidate freeze; exact candidate identity fixed | `ASSURE` | Reviewer then Verifier run against that candidate. |
| `EXECUTE` | Material requirements or scope change | `DEFINE` | The Define revision must be updated and accepted. |
| `EXECUTE` | `reporting_only` or `cancelled` closeout | `INACTIVE` | A success claim is forbidden. |
| `ASSURE` | Reviewer `CHANGES_REQUIRED`, or Verifier failure requiring candidate changes | `EXECUTE` | Candidate rework is required. |
| `ASSURE` | Reviewer or Verifier finding requiring material specification or scope revision | `DEFINE` | The Work Block returns to Define. |
| `ASSURE` | Repeated assurance after fixing only an evidence or verification problem, with unchanged candidate identity | `ASSURE` | No candidate change is allowed for this transition. |
| `ASSURE` | `success` with Reviewer and Verifier `READY` for one exact candidate identity; or `reporting_only`; or `cancelled` | `INACTIVE` | Closeout is recorded as an immutable event. |

Critic rejection remains in `DEFINE` or may close out as `reporting_only` or
`cancelled`. An unknown state or transition fails closed. Controller generation
cannot change while a Work Block is active.

## Policy decision contract

Policy normalizes an event and evaluates it through one canonical evaluator.
It returns `ALLOW` or `DENY` with a reason. Work Block write-set rules and
External Hard Stops are distinct checks in that evaluator.

| Operation class | Decision contract |
|---|---|
| External Hard Stop | `DENY` without the separate required authority: controller activation; controller materialization; installation or copying of controller files into live hook or runtime paths; modification of live controller configuration or the live control surface; protected or default branch mutation; merge; deploy; force push; credentials or secrets mutation; production or live-data mutation; infrastructure mutation; explicit governance override; or any source write outside the admitted write-set. |
| Ordinary inert controller source work | Refactoring the inert package inside the exact WB-033 write-set `.agent/controllers/v1/**` is not itself an External Hard Stop. `ALLOW` requires all of: an active Work Block; write gate `READY`; current branch equal to the exact subject branch; valid lifecycle state; target path inside the exact write-set; no controller materialization or activation; no live hook, runtime, configuration, or control-surface change; and no other External Hard Stop. |
| Subject-branch publication | `git push` is not executed by WB-033 and is not denied solely by its command name. A possible `ALLOW` requires the exact current subject branch, a non-default and non-protected branch, non-force exact publication, an exact assured candidate, required Reviewer and Verifier `READY`, and no External Hard Stop. |
| Ambiguous or unsafe publication | `DENY` for force, multi-ref, default or protected branch, non-subject branch, or otherwise ambiguous push. |

> Editing the inert controller source package is not controller activation. Activation begins only when controller artifacts are installed, materialized, referenced by, or otherwise connected to live runtime/control-surface paths.

The controller policy allowance itself remains limited to inert controller
source; the separate commit-hook amendment above does not alter it. It does
not extend to `.agent/hooks/**`,
`.codex/**`, `.claude/**`, `.agent/active-work-block.default.json`,
`.agent/controller-manifest.json`, or any other live path. The publication row
defines future controller policy semantics only. The Owner subsequently
authorized a non-force push of the exact subject branch after required
assurance, subject to the live publication gate; no push is authorized before
that gate is `READY`.

## Candidate and evidence identity contract

`candidate_id` is the Git tree SHA and is the sole authoritative content
identity for the Reviewer and Verifier candidate. A commit SHA, when present,
may be retained only as provenance and is not a competing candidate identity.
WB-033 does not require an uncommitted assurance candidate. If implementation
would require one, that is a material design change requiring a return to
`DEFINE`.

The minimum role evidence record contains:

- `work_block_id`;
- `role`;
- `verdict`;
- `subject_revision`;
- `candidate_id`, when applicable;
- `session_id`;
- `runtime`;
- `isolation_method`;
- `dispatched_at` and `completed_at`;
- `capability_probe_id` and `capability_observed_at`;
- `report_path`;
- `findings`;
- pre-run and post-run repository and control-surface observations.

Completed evidence is immutable and never expires. Capability freshness is
checked only immediately before a new role dispatch. No artifact requires its
own future hash, a future commit SHA, or a self-referential ledger. If a report
hash is needed, it is calculated after report creation and stored in a separate
referencing record.

## Atomic persistence and bounded recovery contract

Before persistence, the proposed state is fully validated and serialized in a
deterministic representation. Persistence writes a temporary file in the same
filesystem and directory boundary, flushes and syncs where supported by the
existing implementation, and atomically replaces the target. If the result of
replacement is uncertain, the operation fails closed and claims success only
after a fresh read and validation. Invalid state is never persisted as
authoritative state.

Tests use only fixtures or temporary directories and never modify live SSOT.

Automatic recovery is allowed only when canonical `INACTIVE` can be proved.
Active, corrupted, or authority-ambiguous state returns fail-closed/STOP;
recovery does not reconstruct active Work Block authority, Critic, Reviewer,
or Verifier evidence from guesses or Git history.
